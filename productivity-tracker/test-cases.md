# Тест-кейсы — Productivity Tracker

Ниже ключевые тест-кейсы с применением техник тест-дизайна. Номера TC совпадают с автотестами в папке [`autotests`](autotests/): по номеру легко найти автоматизированную версию. В автотестах проверки идут через API, если в кейсе не указано иное.

**Техники тест-дизайна:**
- **Классы эквивалентности** — email и пароль: валидные / невалидные группы значений.
- **Граничные значения** — длина пароля (5 / 6 и 100 / 101 символ), длина имени (50 / 51), длина цели (200 / 201), время (23:59 / 24:00).
- **Негативное тестирование** — пустые поля, пробелы, неверные типы данных, чужие id.
- **Проверка прав доступа** — пользователь не видит и не меняет чужие данные.

### TC-01. Успешная регистрация
| | |
|---|---|
| **Приоритет** | High |
| **Предусловия** | Пользователь не зарегистрирован, открыта страница `/register` |
| **Шаги** | 1. Ввести имя «Андрей»<br>2. Ввести email `andrey.qa@test.ru`<br>3. Ввести пароль `secret12` и повторить его<br>4. Нажать «Зарегистрироваться» |
| **Ожидаемый результат** | Открывается главная страница, видны «Цели на сегодня» и кнопка «Выйти». API: `201`, в ответе есть токен, нет пароля |
| **Статус** | ✅ Passed (при заданной `JWT_EXPIRE`, см. BUG-001) |

### TC-04. Валидные email (классы эквивалентности)
| | |
|---|---|
| **Приоритет** | Medium |
| **Тестовые данные** | Валидные: `info@shop.online`, `info@company.info`, `user+qa@gmail.com`<br>Невалидные: `mail.ru`, `@mail.ru`, `user@`, `user@mail`, пустая строка |
| **Шаги** | Для каждого значения отправить форму регистрации |
| **Ожидаемый результат** | Валидные принимаются, невалидные — сообщение «Введите корректный email» |
| **Статус** | ❌ Failed: `.online`, `.info`, `+` отклоняются → [BUG-004](bug-reports.md#bug-004) |

### TC-05. Длина пароля (граничные значения)
| | |
|---|---|
| **Приоритет** | High |
| **Тестовые данные** | Допустимо 6–100 символов. 5 → ошибка; 6 → успех; 100 → успех; 101 → ошибка |
| **Ожидаемый результат** | 5 символов: `400` «Пароль должен быть минимум 6 символов». 101 символ: `400` с сообщением о максимальной длине |
| **Статус** | ❌ Failed: 5 / 6 / 100 работают верно, но 101 → `500` и неверный текст «минимум 6 символов» → [BUG-008](bug-reports.md#bug-008) |

### TC-07. Длина имени (граничные значения)
| | |

### TC-15. Время активности (граничные значения, API)
| | |
|---|---|
| **Приоритет** | Medium |
| **Тестовые данные** | `23:59` → принимается; `24:00` и `25:99` → отклоняются |

### TC-19. Доступ к чужой активности
| | |
|---|---|
| **Приоритет** | High (безопасность) |
| **Предусловия** | Пользователь A создал активность с id = N. Пользователь B авторизован |
| **Шаги** | От имени B: 1. `GET /api/activities/single/N`<br>2. `PUT /api/activities/N`<br>3. `DELETE /api/activities/N`<br>4. От имени A: `GET /api/activities/single/N` |
| **Ожидаемый результат** | Шаги 1–3: `404` (не раскрываем, что запись существует). Шаг 4: запись на месте и не изменена |
| **Статус** | ✅ Passed |

### TC-25. Длина цели (граничные значения, UI)
| | |
|---|---|
| **Приоритет** | Medium |
| **Тестовые данные** | 200 символов → сохраняется; 201 → ошибка |
| **Шаги** | 1. Ввести в поле цели текст из тестовых данных<br>2. Нажать Enter |
| **Ожидаемый результат** | 200: цель в списке. 201: сообщение об ограничении в 200 символов, текст остаётся в поле |
| **Статус** | ❌ Failed: 200 работает верно; при 201 только окно «❌ Ошибка» без причины, поле очищено → [BUG-007](bug-reports.md#bug-007) |

### TC-27. Перенос записи в чужой аккаунт через `userId`
| | |
|---|---|
| **Приоритет** | High (безопасность) |
| **Предусловия** | Пользователи A и B, у A есть активность с id = N, A знает id пользователя B |
| **Шаги** | 1. От имени A: `PUT /api/activities/N` с телом `{"userId": <id B>}`<br>2. От имени B: получить список активностей за дату записи |
| **Ожидаемый результат** | Поле `userId` игнорируется, у B записей нет |
| **Статус** | ❌ Failed: запись появилась у B → [BUG-012](bug-reports.md#bug-012). То же для целей (TC-28) |
